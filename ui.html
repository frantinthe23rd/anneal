Instructions

Using Anneal

Five modes, one machine, and one rule underneath all of it: only one large model can be in memory at a time. Everything below follows from that.

Start here — what the strip is telling you

The pills in the header are the four models: music, speech, chat and image. Each is cold (not loaded, no memory), heating (starting — the process answers long before the weights are in) or hot, with its real memory footprint once loaded.

Music and image are heavy and mutually exclusive: asking for an image while the music model is loaded evicts it, and the next music request pays the load again. Speech and chat are small enough to sit alongside either.

RequestColdAlready hot
Music, draft tier3–4 min load, then ~70 s~70 s for 30 s of audio
Music, high tier3–4 min load, then ~3 min~3 min
Image30–60 s load, then secondsseconds
Speecha few secondsabout a second a sentence
Chat~20 sstreams immediately

Timings above are from a 16 GB machine, the supported floor — more memory is faster, mostly because less of it is spent paging. Anneal warns you before a slow request rather than after, and each model unloads itself once it has been idle for a while — ten minutes for music, five for chat. A host pill appears when the machine is genuinely short of memory, which is the usual reason a job crawls.

If a request is refused

A 409 means the other heavy model is mid-job. Anneal offers to stop it and retry rather than just failing — take the offer, or wait for the job to finish.

Press — a brief becomes a record

Write what you want the record to be: “a short winter album about leaving a coastal town, folk with strings”. Press plans a title, an artist name and a tracklist with varied lengths, writes lyrics for each track, generates the music, and paints a cover.

  • Tracks 1–8. One track is a single and takes a few minutes; eight is most of an hour. The stages are deliberately ordered — all the writing, then all the music, then the cover — so each heavy model loads exactly once however many tracks you ask for.
  • Typical length is a target, not a rule: the planner varies around it, with shorter openers and longer centrepieces.
  • Instrumental skips the lyric stage entirely.
  • Cover art is the only stage that needs the image model, so it runs last.

A press outlives the browser. Close the tab and it keeps going; the record appears in the Library as something you can play through, with a Download that returns the whole thing as a zip — audio, cover and tracklist. The masters are FLAC, so asking for MP3 transcodes from the original rather than from another lossy copy.

If the gateway restarts mid-press, the record is marked interrupted rather than left claiming to work. Resume keeps the finished tracks and redoes only what is missing.

Music

Describe the track as you would to a session player: genre, instruments, mood, production. “warm lo-fi hip hop with rhodes piano and vinyl crackle” works; “good song” does not.

  • Vocals. Instrumental by default. Choose Write lyrics and either type them or press Write for me, which drafts from your style prompt using the chat model and streams into the box. Click again to stop; your own text comes back if it fails.
  • Section tags matter: [verse], [chorus], [bridge]. They are what the model uses to build structure.
  • Takes generates several variations from one request — cheaper than several requests, because the model is already loaded.
  • Model. draft is distilled for speed (8 steps). high is the fine-tuned model at 50 steps: roughly twice the time, more high-frequency detail. Whether it sounds better is a judgement for your ears. Switching tiers restarts the backend, so the next request pays a cold load.
  • Planning pass runs a small language model first to decide sections, key and arrangement. About 30 s slower, usually better structured. Off, the model improvises the whole take in one go.
  • BPM and key are optional. Left blank, the planner picks them from your description.
Two things that surprise people

The bpm and key in a result are intent, not measurement. They are what the planner asked for, not an analysis of the audio — it can ask for 300 bpm on a take that plainly sits near 100. Set them explicitly if you need them to mean something.

Generation is not deterministic, even with a fixed seed, because the planner samples at temperature. Two identical requests give two different tracks. Comparing takes tells you about the takes, not about the settings.

Speech, image and chat

Speech

28 voices. The prefix is the accent and gender — a American, b British, then f female or m male, so bf_emma is a British woman and am_michael an American man. Speed runs 0.5×–2×. It is fast enough to use in a loop, which is the point of it.

Image

FLUX schnell is distilled for four steps; more steps mostly cost time. Smaller sizes are proportionally faster, so draft at 512 and commit at 1024 or above. The backdrop on the front door was made here.

Chat

A plain conversation with the local Gemma model, streamed, with the transcript kept in your browser rather than on the server. Replies render as Markdown. Show reasoning is off by default: with it on, a short answer can spend its whole budget thinking before it says anything. Enter sends, Shift+Enter starts a new line, and New conversation forgets everything above.

The Library

Everything generated is saved on the server, whoever asked for it — the UI, a curl command or an agent — under outputs/, named from the prompt and paired with a JSON sidecar holding the settings that produced it. Sidecars rather than a database, so the metadata travels with the file: copy the directory anywhere and it stays self-describing.

  • Details shows exactly what produced a file: every submitted parameter, the full prompt and lyrics, which checkpoints ran, and the planned bpm and key labelled as planned.
  • Reuse loads those settings back into the form, so a good result becomes a starting point.
  • Browsing the Library is served straight off disk and wakes no model.

Small things worth knowing

  • Cmd/Ctrl+Enter submits from any field in the studio.
  • Settings holds your defaults for new work, a read-only view of the server's state, and the API key. It shows rather than edits the server's configuration: a web page should not be rewriting the gateway's environment.
  • Over the tailnet you are already signed in and never see a key prompt. On 127.0.0.1 there is no identity to read, so it asks once.
  • The interface respects prefers-reduced-motion — every transition is switched off in one place.
  • Nothing here calls out to the internet. The page's images, fonts and scripts all come from this server.
For developers and agents

The API

Anneal is a service first. This interface is one client of it — everything you can do here, a build script, a Makefile or a coding agent can do over HTTP.

Why it works this way

The original problem was not “I would like to make music”. It was that the things I was building with coding agents kept needing assets that code cannot produce: a game with no soundtrack, a demo with no voiceover, a UI with placeholder art. Hosted services can fill that gap at the cost of an account, a key, a per-request bill and sending the work off the machine.

So Anneal was an API before it was an interface: something a build could call to get a piece of music, a line of speech or a piece of artwork back, on hardware already sitting on the desk. Press exists because the music turned out to be the part that worked best — good enough that “one call, one finished record” was worth building properly.

Getting in

This server answers at __ORIGIN__. Two ways to authenticate:

  • Tailnet identity. Over Tailscale, the proxy stamps who you are onto every request and Anneal trusts it, because the only route to the port is that proxy. No key, no login — this is how the browser is already signed in.
  • Bearer key — Authorization: Bearer $ANNEAL_KEY — for programmatic clients and for loopback, which carries no identity. The key lives in env.local.sh on the host.

Public without either: /health, /supervisor/status, /supervisor/auth, /docs, /openapi.json and this page. Everything else needs one of the two.

Every response has the same envelope. Check both — an HTTP 200 can still carry code: 500.

{ "data": …, "code": 200, "error": null, "timestamp": 1785881567698 }

Music is a job, not a call

Generation takes minutes, so it is submit-and-poll. Speech and images are ordinary synchronous calls.

curl -X POST "__ORIGIN__/release_task" \
  -H "Authorization: Bearer $ANNEAL_KEY" -H 'Content-Type: application/json' \
  -d '{"prompt": "warm indie pop ballad, brushed drums",
       "lyrics": "[verse]\nStreetlights blur into the rain",
       "audio_duration": 45, "quality": "draft", "audio_format": "flac"}'
# -> {"data": {"task_id": "42f580bc-…"}, "code": 200}

curl -X POST "__ORIGIN__/query_result" \
  -H "Authorization: Bearer $ANNEAL_KEY" -H 'Content-Type: application/json' \
  -d '{"task_id_list": ["42f580bc-…"]}'
# status 0 = queued or running, 1 = done, 2 = failed

Poll every 3–5 seconds; there is no webhook. result is a JSON-encoded string — parse it a second time — and decodes to a list, one entry per take. Each entry's file field is already a complete request path including its query string: append it to the base URL as-is, do not encode it again.

The two failure modes to code for

A 502 while polling means the backend was restarting — the poll failed, not the job. Retry the poll, never resubmit, or you queue duplicate work behind the original. A 409 on submit means the other heavy model is loaded; wait, or stop it explicitly via /supervisor/stop.

One call for a whole record

curl -X POST "__ORIGIN__/v1/press" \
  -H "Authorization: Bearer $ANNEAL_KEY" -H 'Content-Type: application/json' \
  -d '{"prompt": "a short winter album about leaving a coastal town, folk with strings",
       "tracks": 4, "duration": 120, "quality": "draft", "art": true}'
# -> {"data": {"id": "…", "state": "planning"}}

curl "__ORIGIN__/v1/press?id=…" -H "Authorization: Bearer $ANNEAL_KEY"
curl -o record.zip "__ORIGIN__/v1/press/download?id=…&format=mp3&bitrate=320k" \
  -H "Authorization: Bearer $ANNEAL_KEY"

State runs planning → writing → recording → artwork → done. A press survives a gateway restart: anything left mid-flight is marked interrupted, and POST /v1/press/resume finishes it without redoing completed tracks.

Speech and images, synchronously

curl -X POST "__ORIGIN__/v1/audio/speech" \
  -H "Authorization: Bearer $ANNEAL_KEY" -H 'Content-Type: application/json' \
  -d '{"input": "Build finished.", "voice": "bf_emma", "response_format": "mp3"}' -o out.mp3

curl -X POST "__ORIGIN__/v1/images/generations" \
  -H "Authorization: Bearer $ANNEAL_KEY" -H 'Content-Type: application/json' \
  -d '{"prompt": "a lighthouse in a storm, oil painting", "size": "1024x1024",
       "response_format": "path"}'

Ask for path rather than b64_json when the caller is on the same machine or an agent: a megabyte of base64 in a response is a poor use of anyone's context.

As an MCP server

Anneal ships an MCP server so an agent — Claude Code, or anything else that speaks MCP — can use it as tools rather than as an HTTP API it has to be taught. It is stdlib-only, so it needs no environment of its own.

{
  "mcpServers": {
    "anneal": {
      "command": "/Users/jon/dev/AIMusic/mcp_server.py",
      "env": { "ANNEAL_URL": "__ORIGIN__", "ANNEAL_KEY": "sk-aimusic-…" }
    }
  }
}

Tools: service_status, prewarm, unload_models, generate_music, check_music_job, generate_speech, generate_image.

Two choices in there are deliberate, and both are about agents rather than about music. Music submits and returns a job id instead of blocking for minutes, with the tool descriptions telling the agent not to resubmit a slow job. Binary comes back as a file path, not base64, because a 1.3 MB PNG is about 1.7 MB of text in a tool result. The cold-start cost is written into the tool descriptions for the same reason: an agent that does not know a call takes four minutes will conclude it has hung.

Going further

INTEGRATION.md in the repository covers what a spec cannot: cold-start handling, the exact polling contract, reference clients in Python and TypeScript, expected timings, and every failure mode worth handling.

About

What this is

A single Apple silicon Mac that makes music, speech, images and text on demand, for anyone on the tailnet and for anything that can make an HTTP request. Built by Jon Moseley.

The idea

Anneal started as plumbing. I was building things with coding agents, and the gap in what they could produce was never the code — it was everything around it. A game with no music. A demo with no voiceover. An interface with grey boxes where the artwork should be. All of that is available from hosted services, at the cost of an account, a key, a bill per request and your work leaving the building.

The concept was simple enough: put the generative models on hardware I already own, behind one address, and let the development workflow call them directly. A build step that wants a soundtrack asks for a soundtrack. An agent that wants a title card makes one. Nothing is metered and nothing is uploaded.

The music was the part that worked far better than expected. What began as “a track from a prompt” turned into Press: one brief becomes a title, an artist name, a tracklist, lyrics, the finished audio and a cover, in a single call. That is the piece I did not plan and use most.

The interface came last, and it exists for a reason the API cannot cover: judging a generated take by reading JSON is miserable. You need to hear it, look at the cover, and see what settings produced it. Both front doors talk to the same gateway — the browser has no privileged path.

Why “Anneal”

Annealing is heating metal and letting it cool slowly, so it settles into a better state than it started in. It is also, almost exactly, what this has to do with its models: they want more memory than one machine has, so each is heated up on demand and allowed to cool when the work stops. That constraint shapes everything — the ordering of Press's stages, the eviction rules, the warnings before a slow request.

The palette follows the same idea. A forge is dark and the heat is the only light source, so the orange is reserved for things that are genuinely hot or genuinely happening. Nothing decorative is that colour. The plate behind the front door and this page was generated by Anneal's own image model.

What it runs on, and what it doesn't

Apple silicon Macs, macOS, 16 GB of unified memory minimum — the tested floor rather than a recommendation, and a real floor: at 16 GB the music model's footprint already exceeds physical RAM and pages throughout a generation. Around 40 GB of disk for weights, environments and the growing library.

Nothing else works today, for two reasons worth separating. Speech, images and text all run through MLX, which is Apple-silicon only and has no fallback here; ACE-Step is the exception, since it supports CUDA and XPU upstream. And the whole model lifecycle — when to evict, when to refuse, when to warn you about the host — rests on four macOS-only system calls for memory pressure, paging and real process footprint.

Contributions and ports are welcome. It is MIT licensed, the memory calls are four functions behind an obvious interface, and adding a backend is a dictionary entry in services.py rather than a rewrite. The repository's issues carry the reasoning behind each decision, which is the right place to start.
